# Architecture
Serves: ADV-001

## Purpose
Serves: ADV-001
The engine is one board run by any number of servers against one database. This document is
the map: which subsystem owns what, the properties every subsystem may rely on from the
database, where identifiers and time come from, and the error classes every contract uses. It
holds no mechanism of its own; each mechanism is stated once, in the subsystem that owns it.

## Contracts
Serves: ADV-001
Provided: none at this level. Every contract is provided by a subsystem and listed in that
subsystem's document.

Consumed by every subsystem: the database properties below, through the database-access
subsystem's contract.

The subsystems, each with its own document:

| Subsystem | Owns |
|---|---|
| database-access | the bootstrap record, the connection to the database and its transport decision, transactions, the cluster mutex, the database clock, the mapping of database failures onto error classes |
| cluster | servers, leases, the node layout, node occupancy, who's-online, server health, version admission, server removal |
| configuration | the settings registry: keys, kinds, scopes, defaults, values, versions, restart-needed reporting |
| audit | the audit entry and the one way to write and read it |
| http | each server's HTTP listeners, their connection limits and deadlines, and the routes other subsystems mount |

Programs, each a separate process on a server's host: `hadv-service` (the engine),
`hadv-setup` (the setup tool, run by the local operator), `hadv-config` and
`hadv-config-gui` (the runtime configuration tools, run by a sysop). Every program reaches
the database only through database-access; nothing else touches the database.

## Data model
Serves: ADV-001
The database is the board's single source of truth. Every subsystem states its own entities.
Properties every subsystem may rely on, realised by the stack:

- **A transaction** groups reads and writes so that either all of them take effect or none,
  and no other transaction sees a partial result.
- **A compare-and-set** is a write whose predicate names the values it expects; it reports
  whether it changed anything, and a check-then-act is atomic when the check is that
  predicate.
- **An exclusive hold** on an entity row makes other transactions that want to hold or change
  it wait until this transaction ends; **the cluster mutex** is an exclusive hold on the
  single board row, and any operation that changes the layout of the board takes it first.
- **A uniqueness constraint** rejects, inside the transaction, a second row with the same key.
- **The database clock** is the one time source for every stored timestamp and every
  comparison of times across servers; a server's own clock is used only for scheduling its own
  work.
- **An increasing identifier** is generated by the database, never reused, and never goes
  backwards.
- **A notification** is delivered by the database to every connected server after a
  transaction commits, at most once per commit, and may be lost; nothing may depend on
  receiving it. No subsystem in this document uses one.
- **Encryption at rest**: a field marked sensitive is encrypted under the board's
  key-encryption key before it is written and decrypted after it is read; the key never
  enters the database.

Identity sources: server IDs, audit entry IDs and layout positions are increasing identifiers
from the database. Node numbers are assigned by cluster's layout operations under the cluster
mutex. Session identifiers are minted by the surface that starts a session and are opaque
here.

## Behaviour
Serves: ADV-001
The engine's process has the states cluster defines; every other subsystem is passive until
cluster admits the server to the board. Start-up order on every server: database-access reads
the bootstrap record and establishes the connection; configuration loads the registry;
cluster admits the server and holds its lease; http opens the listeners; only then does any
surface accept a caller.

## Failure directions
Serves: ADV-001
Every gate fails closed: an error, a timeout or "no result" from a permission check, a lease
check or an occupancy check is treated as denial. Failures of the database are classified by
database-access and handled by cluster's process states; no subsystem implements its own
retry against the database.

## Multi-node invariants
Serves: ADV-001
Nothing a server keeps in memory is truth; each subsystem lists what it caches and when the
cache is invalidated. Any job that runs on a schedule may run on every server at once and
twice on one server; each subsystem states why its jobs are idempotent.

## Audit
Serves: ADV-001
Every state-changing operator action writes an audit entry through the audit subsystem, in
the same transaction as the change, and fails with it.

## Security considerations
Serves: ADV-001
Trust boundaries: between a caller and a surface (untrusted); between a server and the
database (a server holding credentials is trusted, and the database wire is protected by
database-access); between the local operator of a host and that host's server (trusted for
that server's connectivity only); between a sysop and the board (trusted as their role
allows). Authorisation has one implementation, in the access-control subsystem that the
accounts feature will create; until it exists, the only principals are the local operator
(authenticated by possession of the bootstrap record, reaching only what cluster and
configuration state) and the sysop (authenticated by the runtime configuration tool's login,
which the accounts feature defines).

Error classes, used by every contract and owned here:

| Class | Meaning |
|---|---|
| Unavailable | the database could not be reached, the connection was lost, or the operation passed its deadline; a write's outcome is unknown |
| Conflict | a compare-and-set matched nothing, or a uniqueness constraint rejected the write |
| Refused | a policy check failed; the reason is reported |
| Invalid | an input failed validation |
| Denied | the actor lacks permission, or the permission check itself failed |
| NotFound | the named entity does not exist |
| Fatal | the process cannot run and must stop |

## Negative tests
Serves: ADV-001
- A permission check that errors is treated as denial (every subsystem's own tests prove it for
  its gates).
- A subsystem that reaches the database other than through database-access fails the build's
  dependency check.
